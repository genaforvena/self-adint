# Step 0 — the instrument survey: how to observe `(package → hostname)` on the operator's own phone

**Written 2026-08-15.** Question it answers: *what is the best zero-cost, no-root instrument that
produces a per-app → hostname table with observation counts, on a Xiaomi Redmi 10 (MIUI), where we
hold no shell (our ssh key is not authorised) and the router is instruction-only?*

Every factual claim below carries a source. Where a fact could not be established it says
**UNKNOWN** — an invented CSV column would silently break the parser that is already written
(`tools/adint-aggregate`), so guessing is the one thing this document may not do.

---

## 0. Ranked recommendation

| # | instrument | gives `package`? | gives `hostname`? | counts? | cost | verdict |
|---|---|---|---|---|---|---|
| **1** | **PCAPdroid** (`com.emanuelef.remote_capture`), VPNService mode, **CSV export of the connections log** | **yes** — `PackageName` + `UID` columns | **yes** — `Info` column (SNI / `Host:` / DNS name), no decryption needed | one CSV row per connection → count by grouping | free, GPL-3.0, F-Droid + Play | **primary instrument** |
| 2 | PCAPdroid **PCAP-file dump with "PCAPdroid extensions"** + offline `tshark` on the node | yes (uid + app label in the PCAP trailer; package name only in pcapng) | yes (raw ClientHello SNI) | yes | free, but pcapng is a **paid** feature | **fallback for multi-day runs** — no 8192-connection ring limit |
| 3 | TrackerControl / NetGuard / Rethink (other VPNService apps) | see §3c | see §3c | see §3c | free | secondary / cross-check |
| 4 | Static ad-SDK inventory from Termux (**`pm path`** + APK dex/manifest scan) | yes (package) | **no** — yields *candidate SDKs*, not observed hosts | **no** | free | **complement, never a substitute** |
| 5 | LAN logging resolver (static DNS on his Wi-Fi) | **no** | yes | yes | free | volume cross-check only |
| 6 | `dumpsys netstats` / Android per-app data usage | yes | **no hostnames at all** | bytes only | free | **rejected — cannot answer the question** |

**The decision:** #1 alone answers Step 0's question, and it is the only method that produces the
`(package, hostname)` key the artifact is defined on. #4 runs in parallel (it needs only the ssh key
back) and is used to *falsify* #1's coverage — an app whose APK embeds `com.applovin` but which
never appears in the capture is a live question, not a null. One free by-product of #4 is directly
reusable by #1: **Exodus Privacy's `network_signature` field is a public domain→tracker regex list**
(§4.5) and is exactly the kind of public knowledge `ref/exchange-domains.tsv` is made of.

**Exactly one VPNService app may be active at a time** (<https://developer.android.com/develop/connectivity/vpn>),
so #1 and #3 are mutually exclusive, and #3 and #5 conflict too (TrackerControl forbids Private DNS).
Sequence them; do not run them together.

## 1. PCAPdroid — the primary instrument

Version examined: **1.9.1 / versionCode 91**, `minSdkVersion 23`, `targetSdk 37`, licence GPL-3.0-or-later
(`app/build.gradle` in the source tree at commit `c735049`; F-Droid lists 1.9.1 build 91, 2026-02-23).
Sources: <https://f-droid.org/en/packages/com.emanuelef.remote_capture/> ·
<https://github.com/emanuele-f/PCAPdroid>.
*(The F-Droid page states "Android 5.0 or newer"; `build.gradle` for 1.9.1 says `minSdkVersion 23`
= Android 6.0. The build file is the authority for the current version.)*

### 1.1 Does it attribute connections to the app?

Yes, and that is its headline feature. Docs: *"PCAPdroid is an open source network capture and
monitoring tool which works without root privileges"* … *"PCAPdroid leverages the android VpnService
to receive all the traffic generated by the android apps. No external VPN is actually created, the
traffic is processed locally by the app."*
(<https://emanuele-f.github.io/PCAPdroid/quick_start.html>)

Mechanism, from source: `app/src/main/jni/common/uid_resolver.c` resolves the owning uid via
`getUidQ` — the JNI bridge to `ConnectivityManager.getConnectionOwnerUid()` — on Android 10+, with a
`/proc` fallback on older releases. The uid is then mapped to a package by
`AppsResolver.getAppByUid()`. **The Redmi 10's exact Android level is UNVERIFIED here** (we have no
shell on it); the model shipped in the Android 11 era, so the reliable Q+ path is expected, but the
first CSV settles it — a capture where `UID` is frequently `-1`/`unknown` would be the signature of
the `/proc` fallback failing, and is a thing to check on file 1 rather than assume away.

### 1.2 What the CSV export contains — **exact format**

This is the contract a parser must be written against. It is defined in two places in the source:

**Header** — `app/src/main/res/values/strings.xml`, `translatable="false"` (therefore identical in
every UI language, including Russian):

```
IPProto,SrcIP,SrcPort,DstIp,DstPort,UID,App,PackageName,Proto,Status,Info,BytesSent,BytesRcvd,PktsSent,PktsRcvd,FirstSeen,LastSeen
```

<https://github.com/emanuele-f/PCAPdroid/blob/master/app/src/main/res/values/strings.xml> (string
`connections_csv_fields`). Verified byte-identical across tags v1.7.5, v1.8.0, v1.8.4, v1.8.8,
v1.9.0, v1.9.1 and master. Note the inconsistent casing — `SrcIP` but `DstIp`. The package-name
column landed in **1.7.4**: *"Include the package name in the CSV output (credits: Chris Vanstone)"*
(<https://github.com/emanuele-f/PCAPdroid/blob/master/CHANGELOG.md>); CSV export itself landed in
**1.3.0**: *"Export the connections log to a CSV file"* (same file).

**Conditional 18th column:** if *Malware detection* is enabled in preferences, `,Malicious` is
appended to the header and each row gets `,yes` or `,` (empty). Malware detection is a **paid**
feature (<https://emanuele-f.github.io/PCAPdroid/paid_features.html>), so on a free install the
header has exactly 17 columns — **but the parser must accept 17 or 18 and key on the header, never
on a fixed index.**

**Row writer** — `ConnectionsAdapter.dumpConnectionsCsv()`,
<https://github.com/emanuele-f/PCAPdroid/blob/master/app/src/main/java/com/emanuelef/remote_capture/adapters/ConnectionsAdapter.java#L474>:

```java
builder.append(conn.ipproto);                               builder.append(",");
builder.append(conn.src_ip);                                builder.append(",");
builder.append(conn.src_port);                              builder.append(",");
builder.append(conn.dst_ip);                                builder.append(",");
builder.append(conn.dst_port);                              builder.append(",");
builder.append(conn.uid);                                   builder.append(",");
builder.append((app != null) ? app.getName() : "");         builder.append(",");
builder.append((app != null) ? app.getPackageName() : "");  builder.append(",");
builder.append(conn.l7proto);                               builder.append(",");
builder.append(conn.getStatusLabel(mContext));              builder.append(",");
builder.append((conn.info != null) ? conn.info : "");       builder.append(",");
builder.append(conn.sent_bytes);                            builder.append(",");
builder.append(conn.rcvd_bytes);                            builder.append(",");
builder.append(conn.sent_pkts);                             builder.append(",");
builder.append(conn.rcvd_pkts);                             builder.append(",");
builder.append(Utils.formatMillisIso8601(mContext, conn.first_seen));  builder.append(",");
builder.append(Utils.formatMillisIso8601(mContext, conn.last_seen));
```

Column semantics the parser must respect:

| column | type / content | trap |
|---|---|---|
| `IPProto` | **integer** IP protocol number (`6`, `17`, …) — `ConnectionDescriptor.ipproto` is `int` | it is *not* the string `TCP` |
| `SrcIP` | always the PCAPdroid virtual interface address, `10.215.173.1` in VPN mode — FAQ: *"As PCAPdroid acts like a proxy, all the connections have this source address"* (<https://emanuele-f.github.io/PCAPdroid/faq.html>) | carries no information; DNS goes to virtual `10.215.173.2` |
| `UID` | raw Linux uid, `int` | **the robust key** |
| `App` | `ApplicationInfo.loadLabel(pm)` — the localized **display label** | may contain a comma → shifts every later column |
| `PackageName` | `ApplicationInfo.packageName` | empty when the uid is unresolvable; **fake tokens** for virtual uids (see below) |
| `Proto` | nDPI L7 protocol name, or the L3/L4 name when nDPI says UNKNOWN; `HTTPS`/`IMAPS`/`SMTPS` when an ALPN was seen; may contain a dot (`TLS.Google`) | not an enum you can whitelist |
| `Status` | **localized** label — one of `Active` / `Closed` / `Unreachable` / `Error` (English), i.e. `Активно` etc. on a Russian phone | **never match on this string** |
| `Info` | **the hostname** — see §1.3 | may be empty; 256-byte cap |
| `BytesSent` / `BytesRcvd` | `long`, direction from the app's perspective | |
| `PktsSent` / `PktsRcvd` | `int` | |
| `FirstSeen` / `LastSeen` | **ISO-8601 local time with offset**, e.g. `2026-08-15T13:04:21.377+02:00` — `Utils.formatMillisIso8601`, pattern `yyyy-MM-dd'T'HH:mm:ss.SSSXXX` on API ≥ 24 | **not epoch millis**; rendered with the device's primary locale |

Two more properties, both load-bearing:

- **There is no quoting and no escaping anywhere.** The writer is a raw `StringBuilder.append`.
  A comma inside `App` or `Info` shifts the row. **Parse defensively:** split from the left for the
  first 6 fields and from the right for the last 6, and take everything in between as
  `App,PackageName,Proto,Status,Info` — or, safer still, key on `UID` + `Info` and validate the
  field count. A row with more than the expected number of commas must be reported, never silently
  reassembled.
- **The dump respects the current view.** `dumpConnectionsCsv` iterates the adapter's
  `getItemCount()`, so an active search box or an "Edit filter" is applied to the export, and the
  CAB multi-selection exports only the selected rows. **The instruction below therefore tells him to
  clear the search and the filter before exporting** — otherwise a partial file looks exactly like a
  complete one.

**Virtual uids.** `AppsResolver` synthesizes descriptors for kernel/system uids whose "package name"
is a token, not a real package: `-1`→`unknown`, `0`→`root`, `1000`→`android`, `1001`→`phone`,
`1013`→`mediaserver`, `1020`→`multicastdnsresponder`, `1021`→`gps`, `1051`→`netd`, `9999`→`nobody`
(`AppsResolver.java:73-95`). Rows with these must be tagged, not treated as apps. **`netd` (1051) is
the one that matters: on modern Android the system resolver issues DNS on behalf of apps**, so a
`netd` row's `Info` is a hostname with no app attached. Those rows are evidence about the device,
not about a bundle — they belong in `unresolved`/`system`, never merged into a bundle's count.

**No JSON export of the connections list exists.** The connections menu offers exactly one export
item, `save_as_csv` = "Save as CSV" / «Сохранить как CSV»
(`app/src/main/res/menu/connections_menu.xml`, `values-ru/strings.xml:549`). There is a **HAR 1.2**
export (`HarWriter.java`, added in 1.9.0 — *"Export HTTP data in the HAR format"*), but it belongs to
the **HTTP log** view and only carries *decrypted* HTTP requests — irrelevant to us (see §2).

### 1.3 Does it record the hostname without decryption? — **yes**, and this is the crux

`Info` is populated from two independent sources, in `app/src/main/jni/core/pcapdroid.c`:

1. **DNS reverse-lookup at connection creation** (L419): `data->info = ip_lru_find(pd->ip_to_host, &dst_ip)`
   — an LRU filled by parsing DNS **replies** (A/AAAA answers → the query name, L745-762). Flagged
   `info_from_lru = true`.
2. **DPI at first packets** — `process_ndpi_data()` (L548-595) takes nDPI's `host_server_name`, which
   is the **TLS SNI** for `NDPI_PROTOCOL_TLS`, the **`Host:` header** for `NDPI_PROTOCOL_HTTP`, and
   the **DNS query name** for `NDPI_PROTOCOL_DNS`. A DPI value **overwrites** an LRU guess and is
   never overwritten by one.

So the hostname arrives **from the cleartext ClientHello and from cleartext DNS** — no decryption,
no CA, no mitm. F-Droid's own feature list says it: *"Extract SNI, DNS query, HTTP URL, and remote IP
address"* (<https://f-droid.org/en/packages/com.emanuelef.remote_capture/>).

**Provenance is not exported.** `info_from_lru` is not a CSV column, so from the CSV alone you
cannot tell whether a hostname came from the SNI, from a `Host:` header, or from a DNS answer for
that IP. For Step 0 that is acceptable — all three are evidence that *this package talked to this
host* — but it must be stated in the artifact, not assumed away.

**QUIC is a real gap.** The `switch` in `process_ndpi_data` handles only `NDPI_PROTOCOL_TLS`,
`NDPI_PROTOCOL_DNS` and `NDPI_PROTOCOL_HTTP`. A connection nDPI classifies as QUIC therefore gets
**no DPI hostname** — only the DNS-LRU reverse lookup, which is usually right but degrades to empty
when the IP was reached without a fresh DNS answer. Google's ad endpoints are heavy QUIC users.
Mitigation available for free in preferences: **Block QUIC = always**
(`block_quic_mode`, default `never` — `Prefs.java:50-53,101`), which forces apps back onto TCP/TLS
where the SNI *is* parsed. This modifies his traffic (benign, reversible) so it is offered as an
option, not built into the baseline run.

**DoH is handled.** *"PCAPdroid normally detects and blocks DNS-over-HTTPS requests"* in order to
extract the DNS queries (<https://emanuele-f.github.io/PCAPdroid/advanced_features.html>). This is a
decisive advantage over the LAN-resolver method (§3b), which DoH simply bypasses.

### 1.4 Can it run in the background for days? — with two hard limits

**Limit A — the connections ring is 8192 by default.** `Prefs.DEFAULT_CONNECTIONS_LOG_SIZE = 8192`,
`MIN_CONNECTIONS_LOG_SIZE = 1024`, with the source comment: *"The default maximum connections to log
into the ConnectionsRegister. Older connections are dropped. Average Java-heap cost is ~2 KB per
connection … The user can override this via `Prefs.PREF_CONNECTIONS_LOG_SIZE`, bounded by the device
heap"* (`app/src/main/java/com/emanuelef/remote_capture/model/Prefs.java:122-134`). The dropdown's
maximum is computed at runtime — `getMaxConnectionsLogSize()` = `highestOneBit((maxMemory − 8 MB −
max(reserve, 15 %)) / 2 KB)` — so the largest value offered depends on the phone's Java heap.
**The exact maximum offered on his Redmi 10 is UNKNOWN until he opens the dropdown**; the setting is
"Max logged connections" / «Макс. логируемых соединений» (`strings.xml:618`, `values-ru:577`).

Consequence: a busy phone can produce 8192 connections in well under a day, and the oldest are
**silently dropped from the export**. Two mitigations, both in the instruction below: raise the
setting to the maximum offered, and **export at the end of each day rather than once at the end of
the week.** A capture left running for a week and exported once is a sample of the last N
connections, not of the week — and nothing in the file says so. That is exactly the
"sample-is-not-the-interval" failure the mesh doctrine names.

**Limit B — MIUI will try to kill it.** See §3d for the evidence and the settings that prevent it.
PCAPdroid runs as a foreground service with a persistent notification while capturing (VpnService),
which is what keeps it alive; MIUI's autostart/battery-saver policies can still stop it. The
artifact for "it stayed up" is the capture timer in the app's Status tab and the `FirstSeen` span in
the CSV — **not** the operator's recollection.

**Battery/stability cost on MIUI: UNKNOWN.** No source measuring PCAPdroid's battery draw on MIUI
was found. What *is* documented is the memory side: *"Show the full connections payload … This
requires a lot of memory, don't use in the long run"* — the `full_payload` option, which defaults to
**false** (`strings.xml:340-341`, `Prefs.java`). Leave it off. Do not quote a battery figure we have
not measured; the honest plan is to have him report the phone's own battery-usage screen for
PCAPdroid after day 1, which is a measurement rather than a guess.

### 1.5 Can it be filtered to specific apps? — yes, but we do **not** want it

*"Before the capture is started, in the 'Status' tab it is possible to specify an 'App Filter' to
only capture the traffic of the specified app, with only this app being routed inside the
VPNService"* (<https://emanuele-f.github.io/PCAPdroid/quick_start.html>). The UI string is
"Target apps" / «Целевые приложения» (`strings.xml:553`, `values-ru:452`); the preference key is
`app_filter` (a string set) with `app_filter_enabled` default `true` (`Prefs.java`).

For Step 0 the filter must be **empty**: the question is *which* of his apps sell him, and a filter
would presuppose the answer. It is useful later, for a targeted second pass on one bundle.

### 1.6 Where the files land

- **CSV export** goes through the Storage Access Framework: `Intent.ACTION_CREATE_DOCUMENT` with
  `EXTRA_TITLE` pre-filled (`ConnectionsFragment.openFileSelector()`, L1226). **The operator chooses
  the folder** — there is no fixed path. The suggested filename is
  `Prefs.getFilenamePrefix()` + `SimpleDateFormat("dd_MMM_HH_mm_ss")` + `.csv`
  (`Utils.getUniqueFileName`, L775), default prefix `PCAPdroid_` → e.g. **`PCAPdroid_15_Aug_18_42_07.csv`**.
  The month abbreviation is rendered in the device's primary locale, so on a Russian phone it will be
  e.g. `PCAPdroid_15_авг._18_42_07.csv`. Written UTF-8, **no BOM**, LF line endings
  (`ConnectionsFragment.dumpCsv()`, L1189).
- **PCAP dump** (dump mode "PCAP File"): *"The file name and path can be selected after clicking the
  start button"* (<https://emanuele-f.github.io/PCAPdroid/dump_modes.html>); the API default target
  is `Download/PCAPdroid/` (<https://github.com/emanuele-f/PCAPdroid/blob/master/docs/app_api.md>).

### 1.7 The durable fallback: PCAP + "PCAPdroid extensions"

If the 8192 ring proves too small even at the maximum setting, the alternative is **dump mode = PCAP
File** with **`dump_extensions` enabled**: *"Additional metadata to the exported packets. Such
metadata includes the app name and UID of the originating process"*
(<https://emanuele-f.github.io/PCAPdroid/advanced_features.html>), read on the node with
`tools/pcapdroid.lua` in tshark
(<https://github.com/emanuele-f/PCAPdroid/blob/master/tools/pcapdroid.lua>).

Caveat established from that plugin's source: in the **PCAP** encapsulation the trailer carries only
`pcapdroid.uid` and `pcapdroid.appname` (`local appname = trailer(8, 20):raw()` — a **20-byte** app
*label*, truncated). `pcapdroid.packagename` appears only in the **pcapng** custom block
(`uid` bytes 0-3, `packagename_len` byte 4, `appname_len` byte 5, then the two strings) — and
**pcapng is a paid feature** (<https://emanuele-f.github.io/PCAPdroid/paid_features.html>). So the
free PCAP path gives `uid` + a truncated label, and the uid→package mapping has to be reconstructed
separately (e.g. from the CSV of the same session, or from `pm list packages -U` once the Termux
shell is back). Ranked second for that reason.

### 1.8 Scriptable control (noted, not recommended yet)

PCAPdroid exposes an Intent API on `com.emanuelef.remote_capture/.activities.CaptureCtrl` with
actions `start` / `stop` / `get_status` and extras including `pcap_dump_mode`, `app_filter`,
`pcap_name`, `pcap_uri`, `snaplen`, `max_dump_size`, `dump_extensions`, `tls_decryption`,
`api_key`; *"PCAPdroid will ask for user consent every time a capture is started, unless a valid
`api_key` is provided"*
(<https://github.com/emanuele-f/PCAPdroid/blob/master/docs/app_api.md>). Whether Termux's `am` can
drive this from a background shell on Android 11 (background-activity-start restrictions) is
**UNKNOWN and untested**. It is not part of the first pass; it is the automation path if the manual
export loop proves too heavy for him.

## 2. The mitm mode — and why we do **not** need it

PCAPdroid can decrypt TLS via a bundled mitmproxy in a separate free addon (PCAPdroid-mitm), with a
CA generated at runtime. The blocking fact is Android's own policy, quoted by the PCAPdroid guide:

> *"Starting from Android 7, when targeting the Android SDK 23 or later, apps no longer trust any
> user-installed certificates and instead rely only on the system-installed certificates."*
> — <https://emanuele-f.github.io/PCAPdroid/tls_decryption.html>

and the FAQ is blunter still:

> *"For most apps, you will need a rooted device to successfully decrypt TLS traffic."*
> — <https://emanuele-f.github.io/PCAPdroid/faq.html>

The guide's own assessment is that *"decryption on common apps will not usually work"* without
extra steps (system CA via Magisk, APK patching with apk-mitm, or defeating certificate pinning with
JADX) — all of which require root or repackaging his apps. Chrome is named as *"a relatively easy app
to decrypt"*; ad SDKs inside third-party apps are the opposite case.

**How much ad-SDK traffic is actually decryptable on an unrooted MIUI phone: effectively none, and
the exact fraction is UNKNOWN.** We will not measure it and we will not claim it.

**Is decryption needed for our question? No.** Step 0 asks *which exchange endpoints his apps talk
to*. The endpoint identity is in the **SNI**, which is cleartext in the ClientHello, and in the
**DNS query**, which PCAPdroid forces into the clear by blocking DoH (§1.3). Decryption would add
the *contents* of the bid request — valuable for later steps, not for the exchange-selection
decision this step exists to make.

Two caveats on the "SNI is cleartext" assumption, stated so they are not silently assumed away:

- **Encrypted ClientHello (ECH)** standardises hiding the SNI (RFC 9849,
  <https://datatracker.ietf.org/doc/rfc9849/>). Its deployment share on mobile ad-SDK endpoints in
  2026 is **UNKNOWN**. If a meaningful fraction of connections come back with an empty `Info` and a
  `Proto` of `TLS`, that is the signature to look for — and the DNS-LRU path still names the host in
  most such cases.
- **A hostname names the endpoint, not necessarily the auction.** See §5.

## 3. Alternatives, with the same evidence standard

### 3a. Android per-app data usage / `dumpsys netstats` — **rejected, it has no hostname dimension**

`dumpsys netstats` (and `dumpsys netstats detail`) reports usage since boot, with per-UID metrics
`rxBytes / txBytes / rxPackets / txPackets` across the sections *Active interfaces*, *Active UID
interfaces*, *Dev stats*, *Xt stats*, *UID stats*, *UID tag stats*
(<https://developer.android.com/tools/dumpsys>).

**There is no endpoint dimension anywhere in the data model.** The kernel-side accounting is eBPF
maps keyed only by UID, socket tag and interface — `traffic_tag_stats_map`, `traffic_uid_stats_map`,
`traffic_iface_stats_map` — with byte/packet counters as values
(<https://source.android.com/docs/core/data/ebpf-traffic-monitor>). `NetworkStatsService` keeps
exactly four recorders (DEV / XT / UID / UID_TAG). The public API agrees: `NetworkStats.Bucket`
exposes uid, tag, state, metered, roaming, rx/tx and timestamps — and nothing resembling a
destination (<https://developer.android.com/reference/android/app/usage/NetworkStats.Bucket>).

**And Termux cannot run it anyway.** `dumpsys` on a system service goes through `Binder.dump()`,
funnelled through `DumpUtils.checkDumpPermission()`, which requires `android.permission.DUMP`
(<https://github.com/aosp-mirror/platform_frameworks_base/commit/fe9a53bc45fd0124a876dc0a49680aaf86641d3e>).
That permission is `signature|privileged`, "not for use by third-party applications" — Termux is an
ordinary app; the observed failure shape is `Permission Denial: can't dump … due to missing
android.permission.… permission` (<https://github.com/termux/termux-app/issues/2269>). `adb shell`
*would* succeed, because `com.android.shell` (uid 2000) declares `android.permission.DUMP` in its
manifest
(<https://raw.githubusercontent.com/aosp-mirror/platform_frameworks_base/main/packages/Shell/AndroidManifest.xml>)
— **but it buys nothing: even with adb the output is bytes per uid, never endpoints.**

*Evidence caveat carried forward from the sweep:* the current AOSP `NetworkStatsService.dump()` body
could not be fetched line-by-line, so "never any hostname" rests on the data-model documents above,
not on a read of `dump()`. Confidence high, flagged rather than asserted as verified.

**Verdict: wrong instrument at any privilege level.**

### 3b. A logging resolver on the LAN — hostnames without the package

**Private DNS (DoT) cannot practically point at our LAN resolver.** Android's Private DNS strict mode
takes a *hostname*: *"Users can enter a hostname if they want to use a private DNS provider. Android
then sends all DNS queries over a secure channel to this server or marks the network as 'No internet
access' if it can't reach the server"*
(<https://android-developers.googleblog.com/2018/04/dns-over-tls-support-in-android-p.html>). DoT
rides TLS and *"Literal IPv4 and IPv6 addresses are not permitted in `HostName`"*
(<https://developers.google.com/speed/public-dns/docs/secure-transports>). It is also a **global**
setting, not per-Wi-Fi. **UNKNOWN:** the exact AOSP certificate-validation policy for strict mode
could not be sourced primary; practically our resolver would need a publicly-valid certificate for a
resolvable hostname.

**Per-Wi-Fi static DNS works, at the price of a static IP.** To set DNS 1 / DNS 2 on one SSID you
must open the saved network → "Show advanced options" → **IP settings → Static**, which also forces
IP/gateway/prefix (<https://www.askvg.com/how-to-use-custom-domain-name-system-settings-in-android-mobile-phones/>,
<https://support.nordvpn.com/hc/en-us/articles/20041353789585-Change-your-DNS-servers-on-Android>).

**What such a log gives:** timestamp, query name, type/class, **client IP**. Pi-hole's long-term DB
stores `timestamp, type, status, domain, client, forward, reply_type, reply_time, dnssec`
(<https://docs.pi-hole.net/database/query-database/>); unbound's `log-queries` *"prints one line per
query to the log, with the log timestamp and IP address, name, type and class"*
(<https://unbound.docs.nlnetlabs.nl/en/latest/manpages/unbound.conf.html>); dnsmasq's
`log-queries=extra` adds *"a serial number which ties together the log lines … and the IP address of
the requestor"* (<https://thekelleys.org.uk/dnsmasq/docs/dnsmasq-man.html>); AdGuard Home has a
`querylog:` block (<https://github.com/AdguardTeam/AdGuardHome/wiki/Configuration>).

**What it structurally cannot give — and this is why it is not the primary instrument:**
- **No app attribution at all.** The client field is the phone's single LAN IP; none of those
  schemas has a package/uid dimension. The artifact Step 0 demands is keyed by bundle.
- **Blind to hardcoded-IP connections** (no query is ever emitted) and to answers served from the
  phone's own resolver cache.
- **Blind to app-level DoH.** Chrome resolves DNS itself over HTTPS and auto-upgrades when the
  configured system resolver matches a known DoH provider
  (<https://www.chromium.org/developers/dns-over-https/>); the DoH decision is made by the
  *application*, not by the OS or the user (<https://arxiv.org/abs/2204.03975>). A plain LAN dnsmasq
  is not on Chrome's provider list so auto-upgrade should not fire, but any app with a hardcoded DoH
  endpoint is invisible regardless. **PCAPdroid does not have this blind spot** — it detects and
  blocks DoH in order to read the queries (§1.3).
- **It is also mutually exclusive with option 3c in practice:** TrackerControl states that *"Android's
  'Private DNS' is not supported alongside TrackerControl"*
  (<https://github.com/TrackerControl/tracker-control-android/blob/master/README.md>).

**Verdict: keep as a later cross-check on volume, exactly as `docs/step0-method-2026-08-15.md`
already ruled. It cannot produce the Step 0 artifact.**

### 3d. What Termux can do without root — and MIUI's background killing

Termux is an ordinary app: it has no `android.permission.DUMP`, so the `dumpsys` family is closed
(§3a). What it *can* do is package enumeration and APK reading — that is §4.

**MIUI will try to kill a long capture.** dontkillmyapp places Xiaomi/MIUI *"in the most troubled
group on the market with respect to non-standard background process limitations"* and prescribes
three actions: lock the app in Recents (drag the card down); **Security app → Permissions →
Auto-start** (off by default); **Settings → Additional settings → Battery & performance → Manage
apps' battery usage → Saving power in the background → <app> → No restrictions**. It also flags
**MIUI Optimizations** in Developer options as something that *"can break the background tasks"*
(<https://dontkillmyapp.com/xiaomi>). These are exactly steps 6–7 of the Russian instruction below.

**MIUI-specific restriction on always-on VPN: UNKNOWN.** Android's always-on VPN is a standard
platform feature since API 24, started and stopped by the system
(<https://developer.android.com/develop/connectivity/vpn>). Only anecdotal reports of MIUI dropping
VPNs were found (<https://vpncentral.com/vpn-not-working-redmi/>,
<https://github.com/AdAway/AdAway/issues/2919>); neither is authoritative. Not treated as
established, and the instruction does not depend on always-on.

## 4. The static angle — Termux, `pm`, and APK ad-SDK signatures

This lane produces a **candidate map** — which ad SDKs each installed app *embeds*. It is not a
substitute for §1 and it never yields observation counts. Its value is as a **falsifier**: an app
whose APK carries `com/applovin/` but which never appears in the capture is an open question about
coverage, not a null result. It needs only the ssh key back on Termux (ask **A** in
`docs/step0-method-2026-08-15.md`).

**None of this has been executed against the phone** — `redmi-10` is offline on the tailnet (last
seen 49 d) and rejects our key at `<phone-lan-ip>:8022`. What follows is a design with its
preconditions verified against AOSP source, not an artifact.

### 4.1 `pm` from an unrooted Termux shell — works, with one non-obvious incantation

Exec'ing `/system/bin/pm` (→ `cmd package`) from an app domain-transitions to `system_server`, which
is then denied read/write on the pty `untrusted_app` created — so a bare `pm list packages` fails and
everyone concludes it needs root. Both redirections are required
(<https://github.com/termux/termux-packages/discussions/8292>, with the literal
`avc: denied { read write } for path="/dev/pts/0" … scontext=u:r:system_server:s0 … app=com.termux`):

```bash
pm list packages -3 --user 0 2>&1 </dev/null
pm path com.termux --user 0 2>&1 </dev/null
# → package:/data/app/~~zAi6GFqEAPTkudspFt7usg==/com.termux-XCCktU51me6pb27dF1b82A==/base.apk
```

**Android 11+ package-visibility filtering does not bite Termux.** The filter is a compat change
gated on the *caller's* targetSdk — `@EnabledSince(targetSdkVersion = R)` on
`FILTER_APPLICATION_QUERY = 135549675L` in `PackageManager.java`, consumed by
`AppsFilter.FeatureConfigImpl`
(<https://github.com/aosp-mirror/platform_frameworks_base/blob/android12-release/core/java/android/content/pm/PackageManager.java>,
<https://github.com/aosp-mirror/platform_frameworks_base/blob/android12-release/services/core/java/com/android/server/pm/AppsFilter.java>).
Termux's `gradle.properties` sets **`targetSdkVersion=28`** and its manifest declares neither
`<queries>` nor `QUERY_ALL_PACKAGES` (<https://github.com/termux/termux-app/blob/master/gradle.properties>) —
so the list comes back unfiltered.

**Splits matter:** `pm path` prints `sourceDir` **plus every `splitSourceDirs` entry**, while
`pm list packages -f` prints the base only
(`PackageManagerShellCommand.displayPackageFilePath`, L606 vs L890,
<https://github.com/aosp-mirror/platform_frameworks_base/blob/android12-release/services/core/java/com/android/server/pm/PackageManagerShellCommand.java>).
**Use `pm path` and scan every APK it returns.**

### 4.2 Are the APKs readable without root? — **yes, by exact path**

| path element | mode | owner | others | source |
|---|---|---|---|---|
| `/data/app` | **0771** | system:system | traverse only, **no listing** | `init.rc`: `mkdir /data/app 0771 system system` |
| `/data/app/~~<b64>==/` | **0775** on Android 11/12 (0771 from Android 14) | system:system | listable on 11/12 | `makeDirRecursive(…, 0775)` in PMS android11/android12; tightened in `InstallPackageHelper.java:1863` (android14) |
| `…/<pkg>-<b64>==/` | 0775 | system:system | listable | `PackageInstallerService.prepareStageDir` |
| `base.apk`, `split_config.*.apk` | **0644** | system:system | **world-readable** | `PackageInstallerSession.java:1666,1738` — `Os.chmod(sourcePath, 0644)`, comment *"Grant READ access for APK to be read successfully"* |

SELinux is not the barrier: `system/sepolicy/public/app.te` (android-11.0.0_r48 L279-280,
android-12.0.0_r32 L288-289) carries, under *"# Allow apps to read/execute installed binaries"*,
`allow appdomain apk_data_file:dir r_dir_perms;` and `allow appdomain apk_data_file:file rx_file_perms;`
(<https://android.googlesource.com/platform/system/sepolicy/+/refs/tags/android-12.0.0_r32/public/app.te>).
`untrusted_app` is an `appdomain`.

**⇒ `ls /data/app` fails; `cat <exact path from pm path>` succeeds.** The randomized `~~b64==` name
defeats *enumeration*, not *open*. Preinstalled MIUI apps are not in `/data/app` at all — they live
in `/system/app`, `/system/priv-app`, `/product/app`, `/vendor/app`, world-readable 0755 — which on a
Redmi is the majority of the ad-bearing surface.

**MIUI-specific deviation: UNKNOWN.** Nothing in MIUI changes those DAC modes or that sepolicy, but
Chinese-vendor ROMs are reported to add a dangerous permission
`com.android.permission.GET_INSTALLED_APPS` gating the installed-app list
(<https://github.com/getActivity/XXPermissions/issues/175>). Whether **global** MIUI on a Redmi 10
enforces it against a `cmd package` call from an app uid targeting SDK 28 is **UNKNOWN** and is
decided by one command once the phone is reachable.

**Gate to run first — assert the artifact, not the claim.** A truncated or 0-byte read greps clean
and is indistinguishable from "no ad SDK":

```bash
pm path com.whatsapp --user 0 2>&1 </dev/null | sed 's/^package://' \
  | while read p; do printf '%s ' "$p"; head -c4 "$p" | od -An -tx1; done
# MUST print: 50 4b 03 04   (PK\x03\x04)
```

### 4.3 Reading the signatures out of a DEX

DEX type descriptors are literal slash-form ASCII: `'L' FullClassName ';'`, `FullClassName →
(SimpleName '/')* SimpleName` (<https://source.android.com/docs/core/runtime/dex-format>). So
`com.applovin.sdk.AppLovinSdk` is the byte string **`Lcom/applovin/sdk/AppLovinSdk;`**.
MUTF-8 differs from UTF-8 only for U+0000 and supplementary planes, so ASCII identifiers survive
verbatim. **Grep with slashes; the dot form does not occur** (measured on a real 11.4 MB APK:
`com/google/android/material` → 579 hits, `com.google.android.material` → 0).

Two traps, both measured:
- **Inflate first.** `classes*.dex` are usually DEFLATE-compressed inside the APK, so grepping the
  APK directly returns 0. AGP ≥ 4.2 stores dex *uncompressed* at `minSdk ≥ 28`
  (<https://developer.android.com/build/releases/past-releases/agp-4-2-0-release-notes>), which makes
  a direct grep work for *some* apps — a silent-false-negative machine. Always `unzip -p '<apk>' 'classes*.dex'`.
- **`grep -a` is mandatory.** Without it GNU grep prints `Binary file … matches`, suppresses output,
  and **still exits 0**.

`AndroidManifest.xml` inside an APK is binary AXML with a **UTF-16LE** string pool, so `strings` on
it returns nothing. Decode with `aapt2 dump xmltree <apk> --file AndroidManifest.xml` /
`aapt2 dump badging <apk>` (<https://developer.android.com/tools/aapt2>) or `apktool d -s`.

**Termux tooling, checked against the live aarch64 package index**
(<https://packages.termux.dev/apt/termux-main/dists/stable/main/binary-aarch64/Packages>):
present — `aapt`/`aapt2`, `apktool`, `jadx`, `dex2jar`, `unzip`, `radare2`/`rizin`, `python`+`pip`;
**absent — `dexdump`** (which is exactly what Exodus's reference matcher shells out to), `dextra`,
standalone smali/baksmali. `strings` is *not* in `binutils` (that ships `gstrings`); it is in `llvm`
(~70 MB) — avoid it, `grep -a -o -E` replaces it. `pip install androguard` is plausible after
`pkg install python-lxml python-cryptography clang` but the **end-to-end outcome is UNVERIFIED**.

**Recommended split: enumerate on the phone, analyse on the node.** Pull each APK over ssh, PK-check
it, and run the scan here where `dexdump`/androguard/exodus-standalone are available.

### 4.5 Exodus Privacy as a reusable signature source — and its rot

Public, unauthenticated, machine-readable: `GET https://reports.exodus-privacy.eu.org/api/trackers`
(measured: HTTP 200, 571 866 B, **432 entries**; the upstream
`https://etip.exodus-privacy.eu.org/api/trackers/` carries 715). Top level is
`{"trackers": {"<id>": {...}}}` — an **object keyed by stringified id, not an array** — each entry
carrying `id · name · description · creation_date · code_signature · network_signature · website ·
categories · documentation`. Data is **ODbL 1.0 + DbCL 1.0**
(<https://github.com/Exodus-Privacy/exodus/blob/v1/doc/api.md>). Both a **class-name regex**
(`code_signature`) and a **domain regex** (`network_signature`) exist — the latter is exactly what
maps a captured hostname to a named tracker, and is directly reusable for
`ref/exchange-domains.tsv`.

Three properties that must be carried into any use of it:

1. **Signatures are dot-form, the class list is slash-form; it only works because `.` is a regex
   wildcard** (`re.search("com.applovin", "com/applovin/sdk/X")` → True). **A literal substring match
   against these signatures fails for every entry.** Convert `.` → `[./]`.
   Matcher: <https://github.com/Exodus-Privacy/exodus-core/blob/v1/exodus_core/analysis/static_analysis.py>.
2. **`network_signature` is never used for matching anywhere in the Exodus pipeline** — it is stored,
   served and displayed only. It is data for downstream consumers, i.e. for us.
3. **The list rots, and a clean Exodus result is not a clean app.** Measured against the current SDK
   artifacts: `Vungle` = `com.vungle.publisher.|com.vungle.warren.` while the current SDK ships
   `com/vungle/ads/`; `Facebook Audience` = `com.facebook.audiencenetwork` while the real AAR has only
   `com/facebook/ads/`; `Yandex Ad` = `com.yandex.mobile.ads` misses the new `com/monetization/ads/`
   namespace; the Pangle signature misses `com/bykv/vk/openvk`. Exodus also silently drops any
   tracker whose signature is ≤ 3 chars (`Google Ads`, `Google DoubleClick`, `Xiti`, `CrowdTangle`).

**The Exodus Android app does no on-device analysis** — *"The app downloads reports from the εxodus
platform … and shows them to you app by app"* (its own store description;
<https://f-droid.org/packages/org.eu.exodus_privacy.exodusprivacy/>). If the exact `versionCode` is
absent from the DB it falls back to the **highest reported versionCode** — a report for a different
build, silently. Genuinely offline on-device scanners exist if we ever want one without a shell:
**ClassyShark3xodus** (<https://f-droid.org/packages/com.oF2pks.classyshark3xodus/>) and
**App Manager** (<https://f-droid.org/packages/io.github.muntashirakon.AppManager/>, 989 signatures
compiled in, Aho-Corasick substring matching, works unrooted).

### 4.6 The limit, stated so the artifact cannot be over-read

**SDK present ≠ SDK initialized ≠ endpoint contacted ≠ ad rendered.** Three evidenced mechanisms:

1. **Mediation adapters are bundled wholesale for networks never configured.** AdMob's own consumer
   ProGuard rules keep `* implements com.google.android.gms.ads.mediation.MediationAdapter` and
   `* extends …mediation.Adapter` — every adapter class is force-kept **whether or not that network
   is enabled in the dashboard**, and the waterfall is fetched server-side at runtime. Unity Ads
   alone keeps `com.google.android.gms.ads.MobileAds`, so **that class appears in the dex of an app
   with no AdMob account at all.**
2. **Dead code behind a remote kill switch or a paid tier** is byte-identical to live code.
3. **R8 cuts both ways, per SDK and per version.** Unity/Meta/InMobi/Yandex ship package-wide
   `-keep` rules (nothing renamed); AppLovin ships only `-dontwarn`; AdMob keeps just
   `…ads.internal.ClientApi` plus the mediation interfaces. Google now advises library authors
   *"No broad or package-wide keep rules"*
   (<https://developer.android.com/topic/performance/app-optimization/library-optimization>), so
   today's high detection rate is a transient property of current SDK versions, not a law.

**Therefore: a dex hit is strong evidence of embedding and weak evidence of use; a dex miss is not
evidence of absence.** In the project's own vocabulary, this lane emits `IN`-candidates and
`UNKNOWN`, never `NOT`.

## 5. What **none** of these methods can show

Stated up front so the artifact is not over-read:

1. **Who actually ran the auction.** The device sees the endpoint its SDK dials. In mediation, some
   partners are integrated as on-device **"SDK bidders"** — AppLovin MAX names Amazon, BidMachine,
   BIGO Ads, Chartboost, Digital Turbine Exchange, Google, InMobi, ironSource Ads, Liftoff Monetize,
   LINE, Meta Audience Network, Mintegral, MobileFuse, Moloco, Ogury, Pangle, PubMatic, Smaato,
   Unity Ads, Verve, Yandex, YSO Network
   (<https://support.applovin.com/en/max/mediated-network-guides/sdk-bidder-network-guides>) — and
   those *will* appear in the capture. Partners transacted server-to-server behind a mediator are
   **invisible from the device by construction**. The table therefore under-counts exchanges, in a
   direction we cannot bound from the device. `UNKNOWN`, not `NOT`.
2. **Whether an impression was actually sold, or at what price.** A hostname contact is an ad
   *request*, not a sale.
3. **What was in the bid request** — no decryption (§2). That is what Steps 3–4 of `PLAN.md` are for.
4. **Anything about any other person or device.** By construction: the capture is a VpnService on his
   own handset — *"PCAPdroid only captures the traffic of the Android device where it is running"*
   (<https://emanuele-f.github.io/PCAPdroid/faq.html>) — which is precisely why this method was
   chosen over LAN-side capture (`docs/step0-method-2026-08-15.md`, rejected options 1 and 2).
5. **Ingress-initiated connections.** *"In non-root mode, only egress connections (i.e. started by
   the Android device) are routed into the VPNService and captured"* (same FAQ). Irrelevant here —
   ad calls are egress — but it bounds the claim.
6. **Traffic on another VPN.** *"There's only one active service per user or profile. Starting a new
   service, automatically stops an existing service"* and *"Only one app can be the current prepared
   VPN service"* (<https://developer.android.com/develop/connectivity/vpn>). So while PCAPdroid
   captures, no other VPN app runs — and no other capture app either (§3c). The PCAPdroid FAQ says
   the same from the other side: *"Can I capture the traffic of other VPN apps? Yes! You need a
   rooted device"* (<https://emanuele-f.github.io/PCAPdroid/faq.html>). If he
   normally runs a VPN on the phone, that VPN is off for the duration, and that is a behavioural
   change worth telling him about before he starts.

## 6. The parser contract — writable **before** the first file arrives

Target of the pipeline that already exists (`tools/adint-aggregate`, self-tested with each property
seen red under mutation — `docs/step0-method-2026-08-15.md`):

```json
{"ts":"<iso8601>","source":"<instrument>","device":"<device id>",
 "package":"<android package / app.bundle>","hostname":"<observed host>","count":<int>}
```

Mapping from the PCAPdroid CSV:

| JSONL field | from the CSV | rule |
|---|---|---|
| `ts` | `FirstSeen` | already ISO-8601 with offset; pass through verbatim. For a grouped record use the **minimum** `FirstSeen` in the group. |
| `source` | — | constant, e.g. `pcapdroid-1.9.1-csv` |
| `device` | — | supplied on the command line; the aggregator drops any other device **in the parser, before any buffer** |
| `package` | `PackageName` | **drop the row into a `system`/`unattributed` bucket** when `PackageName` is empty or one of the virtual tokens `unknown root android phone mediaserver multicastdnsresponder gps netd nobody` (§1.2). Never merge `netd` DNS rows into a bundle's count. |
| `hostname` | `Info` | **skip the row if `Info` is empty** and record how many were skipped — an empty `Info` is a *known unknown* and must be counted, not dropped silently. Lowercase; strip a trailing dot. |
| `count` | — | `1` per CSV row, or the group size when pre-aggregating by `(PackageName, Info)` |

Parser rules that follow from the source, each of which would be a silent corruption if omitted:

1. **Read the header line and index by name.** 17 columns normally, **18** when malware detection is
   on. A hardcoded index breaks on the paid build.
2. **No CSV quoting exists in the writer.** A standard `csv.reader` is *safe* to use (it will simply
   see extra fields when a comma appears inside `App`/`Info`), but the field count must be checked:
   `len(row) != len(header)` → parse from both ends (first 6 fields left-to-right, last 6
   right-to-left) and **log the row**, never guess.
3. **`IPProto` is a number.** `6`/`17`.
4. **`Status` is localized** — do not filter on it. `Unreachable`/«Недоступно» rows are still
   evidence of an attempted contact and should be kept, with the status carried through.
5. **`FirstSeen`/`LastSeen` are local time with an offset**, not epoch. Compare as timezone-aware
   datetimes; a naive lexicographic min/max is only safe within one device in one timezone.
6. **Sanity gate on the file itself:** if the row count equals the configured "Max logged
   connections" (8192 by default), the ring **overflowed** and the file is a truncated tail. That
   must be reported as a coverage warning on the artifact, not treated as a complete day.

**Sample line: NOT ESTABLISHED.** No real PCAPdroid CSV row could be sourced. A row constructed from
the writer above would *look* authoritative and would be exactly the invented artifact this document
must not produce. The first real file is the fixture; until then the parser's self-test must use a
fixture built from the field-writer expressions in §1.2, labelled as synthetic.

нужно.

Важно заранее: пока PCAPdroid пишет, **другой VPN на телефоне работать не сможет** — Android
допускает только один VPN одновременно. Если ты обычно держишь VPN включённым, на время сбора он
будет выключен.

### 7.1 Установка

1. Установить **PCAPdroid** — либо из F-Droid: <https://f-droid.org/en/packages/com.emanuelef.remote_capture/>,
   либо из Google Play (пакет `com.emanuelef.remote_capture`). Версия на 2026-08-15 — **1.9.1**.
   Платные функции (Firewall, Malware detection, pcapng) **не нужны**, ничего покупать не надо.

### 7.2 Настройки — сделать **до** запуска (это важнее самого запуска)

Открыть меню слева → **Настройки**:

2. **«Макс. логируемых соединений»** (Max logged connections) — поставить **самое большое значение
   из списка**. По умолчанию 8192, и на активном телефоне этого хватает меньше чем на сутки: старые
   соединения молча выбрасываются, и в выгрузке их уже не будет.
3. **«Показывать полное содержимое»** (Full payload) — **оставить выключенным**. Оно ест память и
   нам не нужно.
4. *(необязательно, но заметно улучшает результат)* **«Блокировка QUIC» (Block QUIC) → «всегда»**. Часть рекламных
   запросов идёт по QUIC, и оттуда имя хоста не всегда достаётся. С этой галкой приложения
   откатываются на обычный TLS, где имя видно. Это меняет способ соединения, но ничего не ломает и
   легко возвращается обратно.
5. **«Целевые приложения» (Target apps) — оставить ПУСТЫМ.** Мы не знаем заранее, какие приложения
   тебя продают; фильтр здесь означал бы, что ответ уже известен.

### 7.3 MIUI — чтобы система не убила захват

MIUI агрессивно убивает фоновые процессы — по классификации dontkillmyapp Xiaomi «в самой проблемной
группе на рынке» (<https://dontkillmyapp.com/xiaomi>). Три действия оттуда, ровно в этом порядке:

6. **Приложение «Безопасность» → Разрешения → Автозапуск (Autostart)** → включить для PCAPdroid.
   По умолчанию он выключен.
7. **Настройки → Расширенные настройки → Батарея и производительность → Выбор ограничений для
   приложений → PCAPdroid → «Без ограничений» (No restrictions)**.
8. В списке недавних задач **закрепить карточку PCAPdroid замком** (потянуть карточку вниз), чтобы
   «очистить всё» её не закрывало.
9. Не смахивать уведомление PCAPdroid — пока оно висит, захват жив.
   *(Если захват всё равно обрывается — в «Для разработчиков» есть переключатель «Оптимизация MIUI»,
   он тоже ломает фоновые задачи. Трогать его только если понадобится.)*

### 7.4 Запуск

10. Вкладка **«Состояние»** → кнопка **«Запустить»**. Android спросит разрешение на VPN — согласиться.
11. Дальше — **обычный день**: открывать те приложения, которыми ты реально пользуешься, включая те,
    где видишь рекламу. Ничего специально делать не нужно; чем обычнее день, тем честнее таблица.

### 7.5 Выгрузка — **в конце каждого дня**, не раз в неделю

12. Вкладка **«Соединения»**.
13. **Убрать фильтр и очистить поиск**: значок лупы — стереть текст и закрыть поиск; значок фильтра
    → **«Изменить фильтр»** → **«Сбросить»**.
    Это обязательно: выгрузка сохраняет ровно то, что показано на экране, и отфильтрованный файл
    выглядит точно так же, как полный.
14. Меню (⋮) → **«Сохранить как CSV»**.
15. Откроется системный выбор папки. Имя уже подставлено, вида `PCAPdroid_15_авг._18_42_07.csv` —
    **менять не надо**. Сохранить в **Downloads** (Загрузки).
16. Отправить файл на узел — любым из двух способов:
    - **Telegram:** «Поделиться» → Telegram → в наш чат, **как файл** («Отправить как файл», не как
      фото/сжатое);
    - **или из Termux по локальной сети:**
      `cp /sdcard/Download/PCAPdroid_*.csv ~ && scp ~/PCAPdroid_*.csv mesh-home@<node-lan-ip>:/home/mesh-home/self-adint/data/raw/`
      (адрес узла в локальной сети — `<node-lan-ip>`; для scp из Termux нужен `pkg install openssh`
      и наш ключ — если ключ ещё не заведён, проще прислать Telegram'ом).
17. После выгрузки — **захват можно не останавливать**, он продолжится. Просто повторить шаги
    12–16 на следующий день.

### 7.6 Что прислать вместе с первым файлом

18. Скриншот вкладки **«Состояние»** — там видно, сколько времени шёл захват (это единственное
    доказательство, что MIUI его не убил).
19. Через сутки — Настройки MIUI → Батарея → расход по приложениям → сколько съел PCAPdroid.
    Мы этого нигде не измеряли и не будем это выдумывать; твоя цифра и будет измерением.
20. И ответ на один вопрос, без которого таблица может оказаться честной и бесполезной:
    **Redmi 10 — это тот телефон, которым ты реально пользуешься каждый день?** Если основной
    телефон другой, мерить надо на нём.

### 7.7 Как всё выключить

21. Вкладка «Состояние» → «Остановить». Уведомление исчезнет, VPN снимется, твой обычный VPN снова
    заработает. Если включал **«Блокировка QUIC»** — вернуть в «никогда». Приложение можно удалить:
    никаких следов в системе, кроме сохранённых CSV, не остаётся.

## 8. The open unknowns — what a reader must not assume this document settled

1. **No real PCAPdroid CSV row has ever been seen.** The format in §1.2 is read out of the writer's
   source, which is the strongest evidence available before file 1 — but the *first* file is still
   the fixture that confirms it. Until then every parser test is labelled synthetic.
2. **The Redmi 10's Android level and MIUI build are unverified** (no shell, no session). This
   decides the uid-resolution path (§1.1), the `/data/app` directory mode (§4.2), and whether
   `GET_INSTALLED_APPS` gates `pm list packages` (§4.2).
3. **Whether the Redmi 10 is the phone he actually lives on.** Asked as step 20 of the instruction.
   Measuring the wrong handset produces a table that is honest and useless.
4. **Battery cost of a multi-day VPNService capture on MIUI: not measured by anyone we can cite.**
   His day-1 battery screen is the measurement; no figure is quoted until then.
5. **The maximum "Max logged connections" his device will offer** — computed at runtime from the Java
   heap (§1.4). Until he reads the dropdown we do not know whether a full day fits in one export.
6. **ECH deployment share on ad-SDK endpoints in 2026** (§2). The signature to watch for is an empty
   `Info` on a `TLS` row.
7. **What fraction of exchanges are transacted server-side and therefore invisible from the device**
   (§5.1). Unbounded from this vantage — the artifact under-counts in a direction we cannot measure,
   which is exactly why `NOT` is never issued from it.
8. **TrackerControl's CSV column set** (§3c) — the reason it is the second opinion and not the first.
9. **Whether Termux's `am` can drive PCAPdroid's Intent API from a background shell on this Android
   version** (§1.8) — untested; not on the critical path.
10. **`androguard` under Termux end-to-end** (§4.3) — plausible, unverified; the node-side analysis
    path makes it unnecessary.
