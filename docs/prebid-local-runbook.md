# prebid-local-first — как это поднимается и что именно является артефактом

Шаг: локальный Prebid Server + минимальное приложение на телефоне оператора. **Регистрация в SSP в
этот шаг не входит** — это следующий, гейтованный шаг. Наружу ничего не открывается.

## Артефакт

`data/bidreq/<ts>-<sha8>.request.json` — **bid request, который составил SDK на его телефоне**, в
том виде, в каком он пришёл на сокет. Рядом:

- `.meta.json` — адрес пира, время, размер, sha256 тела, режим гейта по устройству;
- `.response.json` — что ответил наш Prebid Server;
- `data/bidreq-outbound/<ts>-<sha8>.outbound.json` — что Prebid Server **составил бы покупателю**.

**Почему артефактом не может быть JSON, написанный руками.** Такой файл собирается за полчаса и
выглядит безупречно, но описывает не телефон, а наше представление о телефоне. Смысл шага ровно в
том, что устройство рассказывает о себе **само**: `device.ifa`, модель, версия ОС, экран, тип
соединения, локаль, оператор — всё это заполняет SDK, читая железо, на котором он запущен. Поэтому
в `MainActivity.java` нет ни одной строчки JSON, а `adint-bid-capture` пишет тело **побайтово** и
никогда не пересериализует его: пересериализованный документ — это документ, который написали мы.

**Как проверить, что запрос сделал телефон, а не мы.** В `.meta.json` лежит `peer`. Захват с
`peer_is_localhost: true` сделан на самом сервере — то есть нами. Утверждение «это прислал телефон»
проверяется из артефакта, а не из коммит-мессаджа.

## Состав

```
телефон (приложение с Prebid Mobile SDK)
   │  HTTP POST /openrtb2/auction
   ▼
adint-bid-capture      0.0.0.0:8000   ← пишет тело ПОБАЙТОВО, затем форвардит без изменений
   ▼
prebid-server (Go)     :8001          ← настоящий Prebid Server, НЕ пропатченный
   ▼
adint-stub-bidder      127.0.0.1:8002 ← отвечает 204 (no bid) и пишет исходящий запрос
```

**Почему заглушка, а не настоящий адаптер.** Prebid Server отказывается проводить аукцион без хотя
бы одного биддера, а у каждого настоящего адаптера endpoint смотрит на живую биржу. Направить туда
локальный тест — значит отправить его устройство вместе с `ifa` компании, с которой у нас нет ни
аккаунта, ни его разрешения на контакт. Поэтому endpoint адаптера переопределён на локальную
заглушку, и **за пределы машины не уходит ничего**.

## Запуск

```bash
# 1. Prebid Server (конфиг: ~/prebid-local/cfg/pbs.yaml)
cd ~/prebid-local/cfg && ~/prebid-local/prebid-server-bin

# 2. заглушка-биддер (только loopback; иначе отказывается стартовать)
tools/adint-stub-bidder --listen 127.0.0.1:8002 --out data/bidreq-outbound

# 3. захват. Первый раз — --any-device, потому что GAID ещё неизвестен
tools/adint-bid-capture --listen 0.0.0.0:8000 --upstream 127.0.0.1:8001 \
    --any-device --allow 192.168.8.0/24 --out data/bidreq

# состояние
curl -s http://127.0.0.1:8000/status
```

**Порядок с `--any-device` не косметический.** Первый удачный захват — это то, что **выдаёт GAID**
(он внутри запроса), а GAID — ровно тот вход, на котором стоят письма субъекта данных
(`step0d-letter-templates`). То есть один запуск в bootstrap-режиме закрывает открытый вход, и после
этого гейт пиннится: `--device <GAID>`, и запрос с любым другим `ifa` отказывается **в обработчике,
до диска** (правило 1 — конструкция, а не обещание).

## Приложение

`android/` — один экран, одна кнопка отсутствует, состояния на устройстве нет. Собирается в APK и
ставится на его телефон по adb. Хост Prebid Server зашит на этапе сборки
(`-PpbsHost=http://<LAN-IP>:8000/openrtb2/auction`), чтобы то, с чем говорит APK, читалось из
`app/build.gradle`, а не из скриншота экрана настроек.

Две зависимости, каждая из которых нужна по конкретной причине:

- `org.prebid:prebid-mobile-sdk` — тот самый SDK, который составляет запрос;
- `com.google.android.gms:play-services-ads-identifier` — без него SDK не может прочитать GAID, и
  `device.ifa` приедет пустым. **Пустой ifa выглядит точно так же, как телефон, где пользователь
  отказался его отдавать** — то есть отсутствие зависимости подделало бы отказ, которого не было.

По той же причине в манифесте стоит `com.google.android.gms.permission.AD_ID`: с Android 13
рекламный идентификатор закрыт этим разрешением, и без него читается нулевой GAID.

Ожидаемый результат в приложении — **`NO_BIDS`**, и это не ошибка: единственный биддер локального
сервера — заглушка, отвечающая 204. Артефакт — запрос, а не ставка.

## Хранимые запросы: почему без них 400

Prebid Mobile **не шлёт параметры биддера в запросе**. Он присылает
`ext.prebid.storedrequest.id` (аккаунт) и `imp[].ext.prebid.storedrequest.id` (плейсмент), а всё
остальное — конфигурация на стороне сервера, как у настоящего паблишера. Без файлов в
`~/prebid-local/cfg/stored/by_id/` сервер отвечает `400 Stored Request with ID=... not found`.

Это тоже разделение труда, которое стоит запомнить: **устройство описывает себя, сервер описывает
инвентарь.** В `stored_requests/adint-local.json` и `stored_imps/adint-imp-1.json` нет ни одного
поля про телефон, и наоборот — биддер и его placement приходят не с телефона.

И заметьте: 400 от Prebid Server **не помешал захвату**. Запрос уже лежал на диске, потому что
захват стоит ПЕРЕД сервером, а не внутри него. Артефакт не зависит от того, понравился ли запрос
серверу.

## Что уже проверено (2026-08-15)

Цепочка прогнана насквозь синтетическим зондом **с самого сервера** — и его захват честно помечен
`peer_is_localhost: true`, то есть он не выдаёт себя за телефон. Prebid Server принял запрос,
составил исходящий и отправил заглушке. Разница между входящим и исходящим (343 → 571 байт):

- **добавил** `at` (тип аукциона), `source.tid`, `imp[].secure`, развернул `banner.format` в
  `banner.w/h`, добавил `ext.prebid.channel`, `ext.prebid.server` (`datacenter`, `externalurl`,
  `gvlid`) и переписал `imp[].ext.prebid.bidder.appnexus` в `imp[].ext.appnexus` с
  `placement_id` в змеином регистре;
- **убрал** `imp[].ext.prebid.bidder.*`.

То есть сервер не «пересылает» запрос, а **переписывает** его, и сравнение двух файлов показывает,
что именно он добавляет от себя, а что выбрасывает. Это и есть побочная выгода шага: приёмник шага 1
будет писаться на настоящем формате, а не на примерах из документации.

## Границы, названные честно

- **Публичного доступа нет**: на mesh-home входящий трафик из интернета закрыт и остаётся закрытым.
- **Но `:8001` слушает на всех интерфейсах**, включая tailnet. Это наши же узлы, а не интернет, —
  и всё же это не «ничего не открыто», поэтому написано прямо. Захват на `:8000` обязан быть виден
  из LAN, иначе телефон до него не достучится; `--allow 192.168.8.0/24` сужает круг пиров.
- **Захват С НАСТОЯЩЕГО ТЕЛЕФОНА есть, но это НЕ его телефон.** APK собран и прогнан на Note3
  (SM-N900, Android 5.0) — узле меша, стоящем на USB. Это проверка цепочки, а не измерение его
  профиля, поэтому она пишется в отдельный каталог `data/bidreq-chaintest/`, и `.meta.json`
  честно называет пира `192.168.8.184`. Артефакт по его Redmi всё ещё не получен: нужен его
  телефон на LAN (или на USB) и одна установка APK.

## Прогон с настоящего телефона (Note3, проверка цепочки, 2026-08-15 16:04Z)

`data/bidreq-chaintest/20260815T160408Z-e4674c94.request.json`, 989 байт, пир `192.168.8.184`,
`peer_is_localhost: false`. **Ни одно поле ниже мы не писали** — всё это SDK прочитал с железа:

```
ifa 1910e834-…   make samsung   model SM-N900   os Android   osv 5.0   hwv Samsung SM-N900
carrier "MTS RUS"   mccmnc 250-01   language ru   h 1920   w 1080   pxratio 3
connectiontype 2   devicetype 4   lmt 0   ua Mozilla/5.0 (Linux; Android 5.0; SM-N900 …)
```

Оператор мобильной связи и MCC/MNC приезжают без всякого разрешения на геолокацию — это стоит
запомнить отдельно: `setShareGeoLocation(false)` выключает координаты и **не выключает** сеть, по
которой абонент опознаётся страной и оператором.

**Главный факт прогона: блок `device` проходит через Prebid Server БЕЗ ИЗМЕНЕНИЙ** — сравнение
входящего и исходящего даёт `device` идентичным байт в байт. То есть то, что телефон рассказал о
себе, ровно то и доезжает до покупателя; сервер переписывает обвязку (`at`, `source.tid`,
`imp[].secure`, `displaymanagerver`, `ext.prebid.server`, разворачивает `storedrequest` в реальные
параметры биддера), но описание устройства не трогает.

Note3 — узел меша, не третье лицо, и его захват лежит отдельно от каталога доказательств.
