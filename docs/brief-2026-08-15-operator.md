# Self-ADINT: чтение собственного рекламного профиля со стороны спроса

Статус: черновик под меш. Цель первого прохода — не собрать данные, а выяснить,
что вообще доезжает до покупателя бесплатно.

## Тезис

Вопрос не «сколько я потрачу на показы», а «что мне отдают даром».
Аудиторный профиль приезжает внутри самого bid request. Показы покупать не нужно.

Деньги в этой задаче почти ничего не покупают. Покупает QPS-аллокация,
а она выдаётся за форму поведения сида, не за спенд.

## Два источника, в порядке убывания дешевизны

### A. Пассивное чтение payload (стоимость ≈ 0)

Из каждого запроса, где device.ifa совпадает с целевым:

- user.data[] — сегменты от data-провайдеров, с id провайдера и segtax
- user.ext.eids[] — какие ID-графы уже сшили устройство
- user.ext.consent — TCF-строка, если приезжает
- device.geo + geo.type — класс точности, не координаты как таковые
- app.bundle — какие SDK вообще торгуют этим устройством

Основной результат первого прохода: **распределение geo.type по bundle**.
Не трек перемещений — он на этом сэмпле недостижим. Именно карта того,
какие приложения отдают GPS-класс координаты, а какие IP-класс.

### B. Активный оракул через таргетинг (стоимость ≈ цена показа за бит)

Нужен только для сегментов, живущих внутри платформы и не выезжающих в payload.
Бид с фильтром по сегменту: выиграл → состою. Один бит за долю цента.

Ограничение — не деньги, а пропускная способность:
30–100 оказий в сутки. Порядка 1–3 тысяч бит в месяц при последовательном опросе.

## Оракул трёхзначный

WIN → состою (при условии, что биржа честно применяет таргетинг).

LOSS → **не значит «не состою»**. Мог не выиграть по цене, мог не возникнуть
показ, мог быть таймаут. Отрицательный результат неотличим от отсутствия результата.

Поэтому:

    IN       — один WIN
    UNKNOWN  — по умолчанию
    NOT      — k подтверждённых LOSS подряд

k вычисляется из наблюдаемой частоты собственных показов за окно, не берётся
константой. Пул, вернувший UNKNOWN, не расщепляется — переставляется в хвост очереди.

## Про алгоритмы: где ddmin работает, где нет

**Задача «в каких я сегментах» — не ddmin.** Это group testing.
Если таргетинг умеет OR по списку — один бид тестирует весь пул.
Дорфман / binary splitting: при 2000 кандидатов и ~50 попаданий нужно
порядка 250–300 тестов вместо 2000.

ddmin здесь вырождается в бинарное расщепление, потому что его машинерия
(тест дополнений, повышение гранулярности при провале обеих половин)
существует для немонотонных тестов с интерференцией. Членство в сегменте
монотонно: добавление сегментов в OR не может превратить WIN в LOSS.
Взаимодействия между элементами нет. ddmin платит за то, чего не происходит.

**Задача «какое минимальное подмножество поведения загоняет меня в сегмент X» — вот это ddmin.**
Вход — установленные приложения и посещённые категории. Тест — «я всё ещё в X».
Немонотонность настоящая: убрал одно приложение — вылетел, убрал два — вернулся,
потому что провайдер пересчитал look-alike.

Цена — длина цикла. Каждый тест: изменить поведение → ждать переобучения профиля
(дни) → мерить. ddmin делает O(n²) тестов в худшем случае. При тесте длиной в трое
суток реалистично только n порядка 8–10. Не больше.

С шумным односторонним оракулом ddmin разъедется — он строит рекурсию на отрицаниях.
Прогонять только по сегментам, уже подтверждённым как IN, и только там, где
UNKNOWN удалось свести к NOT.

## Что выяснить до оплаты депозита

Задать бирже напрямую, это нормальные вопросы покупателя:

1. Отдаётся ли user.data[] сидам без истории спенда?
2. Не хешируется и не вырезается ли device.ifa?
3. Есть ли forecast / reach-estimate API? С одним IFA он вырождается
   в тот же оракул 1/0, но без расхода показа. Это важнее ставок и размера депозита.

5. Что в договоре про удержание данных bid request вне целей биддинга.
   Скорее всего прямой запрет — это надо знать до, а не после.

## Порядок работ

1. Приёмник + decoy-биддер, локально, на синтетических запросах.
2. Онбординг сида. Это долгая часть — юрлицо, agreement, вайтлист, переговоры о QPS.
3. Неделя пассивного сбора. Отчёт: что приезжает в user.data, кто в eids,

4. Только если payload оказался пустым или захешированным — думать про активный оракул.
5. Сброс GAID → повтор батареи → кривая восстановления профиля по сегментам.
   Это лучшая демонстрация из всех возможных здесь, сильнее любой тепловой карты.
